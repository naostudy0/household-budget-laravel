# テスト方針

## 目的

LifeLedger のテストは、仕様を安全に育てるために書く。

特に会計単位、取引、仕訳、残高、内部取引の相殺などは、実装の都合よりもドメインルールの正しさを優先する。

一方で、すべての入力パターンや異常系を Feature テストに詰め込むと、テストが遅く、意図も読みにくくなる。

そのため、Feature / Integration / Unit の役割を分け、確認したい仕様に合った層でテストする。

## Agentic TDD の基本方針

実装タスクでは、原則としてテストを先に書く。

基本サイクルは以下とする。

```text
1. Red:       仕様を表すテストを書く
2. Green:     テストを通す最小限の実装を書く
3. Refactor:  テストを保ったまま整理する
```

TDD の最初のテストは、主に Feature テストから始める。

ただし、Feature テストは一般のユーザー体験としてあり得る代表ケースに限定する。

パラメーター改ざん、境界値、細かいバリデーション分岐、悪意あるユーザーを想定した入力パターンの網羅は、原則として Feature テストでは行わない。

これらは、FormRequest、Policy、UseCase、Domain Service、Value Object など、責務を持つクラスの Integration または Unit テストで確認する。

## テスト種別の定義

### Feature テスト

Feature テストは、HTTP リクエストを起点にしたユーザー体験を確認する。

対象は以下とする。

- 画面が表示できる
- Inertia のページ名と主要 props が正しい
- 主要な正常系フローが成功する
- 一般ユーザーが通常操作で遭遇しうる代表的な失敗が確認できる
- 作成、更新、削除後に期待する画面へリダイレクトされる
- ユーザー境界や認可境界として重要な代表ケースが守られる

Feature テストに含めないものは以下とする。

- 入力値の全パターン網羅
- 境界値の詳細確認
- パラメーター改ざんの全パターン
- 悪意あるユーザーの操作を想定した網羅的なケース
- UseCase や Domain の詳細ロジック
- FormRequest のバリデーションルールの全分岐

Feature テストは、ユーザーから見た「この機能が使えるか」を確認する層とする。

### Integration テスト

Integration テストは、実際の DB、Repository 実装、Query、UseCase、FormRequest など、複数の実クラスを組み合わせて確認する。

対象は以下とする。

- UseCase が Repository 実装を通じて正しく保存する
- Query が実 DB から必要なデータだけを取得する
- FormRequest のバリデーションルールが期待通りに動く
- Policy と Model の組み合わせが認可境界を守る
- Repository 実装がドメインオブジェクトや DTO と永続化の橋渡しを正しく行う
- Application 層の処理が Eloquent 実装と組み合わさって動く

Integration テストでは、原則としてモックを使わない。

ただし、メール送信、外部 API、決済、外部ストレージなど、プロセス外への副作用があるものはモックまたは fake を使ってよい。

### Unit テスト

Unit テストは、対象クラスまたは対象メソッドのロジックだけを確認する。

外部クラスへの依存はモックする。

対象は以下とする。

- Value Object の不変条件
- Entity の状態遷移
- Domain Service の計算や判定
- Policy の分岐ロジック
- 純粋な変換、計算、分類ロジック

Unit テストでは DB、HTTP、Eloquent、Laravel のコンテナに依存しない。

ドメインルールが複雑な場合は、Feature テストよりも Unit テストを厚くする。

## クラス種別ごとの判断基準

| 対象 | 主なテスト | 方針 |
|---|---|---|
| Controller | Feature | HTTP 境界、Inertia ページ名、主要 props、リダイレクト、認可の代表ケースを確認する。Controller 内の細かい分岐を網羅しない。 |
| FormRequest | Integration | ルールの全パターンを `Validator` で確認する。Feature では代表的な入力エラーだけを扱う。 |
| UseCase | Integration | 実 Repository 実装と DB を使い、状態変更、払い出される ID、公開識別子、保存値を確認する。 |
| Query | Integration | 実 DB を使い、ユーザー境界、検索条件、並び順、表示用データを確認する。 |
| Repository 実装 | Integration | Eloquent と DB との変換、保存、復元を確認する。単純な CRUD のみなら UseCase テストで兼ねてもよい。 |
| Entity | Unit | ID による同一性、状態遷移、不変条件を確認する。 |
| Value Object | Unit | 値の妥当性、不変性、比較、計算を確認する。 |
| Domain Service | Unit | 会計ルール、残高計算、内部取引の相殺判定などを DB や Laravel に依存せず確認する。Repository などの外部依存を呼ぶ場合はモックする。 |
| Policy | Unit または Integration | 分岐が単純なら Unit、Model や DB との組み合わせを確認したい場合は Integration。代表的なユーザー境界は Feature でも確認する。 |
| Inertia Page | Feature | ページ名、主要 props、通常操作後の遷移を確認する。Vue 内部の表示分岐は必要になった時点でフロントエンドテストを検討する。 |

## FormRequest のテスト方針

FormRequest は Integration テストで全パターンを網羅する。

確認対象は以下とする。

- 有効な入力値が通る
- 必須項目が未指定の場合に落ちる
- 型が不正な場合に落ちる
- 文字数、数値範囲、日付範囲などの境界値
- enum や選択肢に存在しない値
- 複数項目の組み合わせで成立するルール

Feature テストでは、ユーザー体験として重要な代表的なバリデーションエラーだけを確認する。

例として、会計単位名が空の場合に入力画面へ戻ることは Feature テストで確認してよい。

一方で、最大文字数、型不一致、存在しない enum、改ざんされた ID の全パターンは FormRequest の Integration テストに寄せる。

## 認可とユーザー境界のテスト方針

ユーザー境界は LifeLedger の重要な仕様である。

Feature テストでは、一般ユーザー体験として重要な代表ケースを確認する。

- 他ユーザーの会計単位を一覧に表示しない
- 他ユーザーの会計単位を表示、更新、削除できない
- 作成時に Request の `user_id` を信頼せず、ログインユーザーに紐づける
- 認可失敗時に想定したレスポンスになる

Policy の詳細な分岐、Query の検索条件、FormRequest の改ざん入力パターンは、それぞれ Unit または Integration テストで確認する。

Feature テストは「代表的な境界がユーザー体験として守られているか」を見る層であり、攻撃パターンの一覧表ではない。

## ドメインルールのテスト方針

会計ルールは LifeLedger の中心であるため、ドメイン層のテストを優先する。

対象は以下とする。

- 金額が負になってよいか、または許可しないか
- 借方、貸方の整合性
- 仕訳がバランスしていること
- 残高計算
- 会計単位間の内部取引判定
- 合算ビューでの内部取引相殺
- 複数帳簿をまたぐ整合性

これらは、まず Unit テストでドメインルールそのものを確認する。

DB への保存や UseCase との組み合わせが重要な場合は Integration テストを追加する。

Feature テストでは、ユーザーが通常操作で到達する代表的な正常系と、重要な失敗ケースに絞る。

## テスト追加時の判断フロー

新しい仕様を追加するときは、以下の順で考える。

```text
1. ユーザー体験として確認すべきか
   Yes → Feature テスト
   No  → 2へ

2. 実 DB や実クラスの組み合わせが重要か
   Yes → Integration テスト
   No  → 3へ

3. 対象メソッドやドメインルールだけを確認したいか
   Yes → Unit テスト
```

迷った場合は、以下を優先する。

1. ドメインルールの正しさ
2. テストを読んで仕様が分かること
3. 失敗したときに原因を特定しやすいこと
4. Feature テストを増やしすぎないこと

## 完了条件

実装タスクでは、原則として以下を確認する。

- 追加または変更した仕様に対応するテストがある
- 対象テストが Green である
- `php artisan test` が Green である
- `./vendor/bin/pint --test` が Green である
- フロントエンドを変更した場合は `npm run format:check` が Green である

ドキュメントのみを変更した場合は、テスト実行を省略してよい。
