# 認可方針

## 目的

LifeLedger では、ユーザーごとのデータ分離を認可の基本方針とする。

他ユーザーの会計単位、取引、振替を参照または操作できないことを、Controller と Query の境界で明示的に保証する。

認可はドメインルールとは分離する。Domain 層は「会計として正しいか」を扱い、HTTP / Application / Query 側は「そのユーザーが操作してよいか」を扱う。

## 初期スコープ

初期段階で扱う認可対象は以下とする。

- 会計単位
- 取引
- 振替
- 一覧、検索、集計などの読み取り処理

以下は初期段階では対象外とする。

- 管理者ロール
- 組織、チーム、共有会計
- 課金プランによる機能制限
- ベータ機能の公開範囲制御

これらが必要になった時点で、Gate または専用の認可設計を追加する。

## Policy / Gate の使い分け

Policy は、特定のモデルまたはリソースに対する参照・作成・更新・削除の認可に使う。

対象例は以下とする。

- 会計単位の `viewAny`, `view`, `create`, `update`, `delete`
- 取引の `viewAny`, `view`, `create`, `update`, `delete`
- 振替の `viewAny`, `view`, `create`, `update`, `delete`

`viewAny` は、認証済みかどうかだけを確認するためには使わない。その場合は `auth` ミドルウェアに任せる。

`viewAny` は、将来のロール、プラン制限、機能公開範囲など、一覧画面そのものを表示してよいかを判断する必要が出た場合に使う。

初期段階で `viewAny` に実質的な条件がない場合は、Policy に空に近い実装を増やさず、Controller の `auth` ミドルウェアと Query のユーザー境界で保証する。

Gate は、特定のモデルに自然に結びつかない機能単位の認可に使う。

初期段階では Gate の実装を増やしすぎない。将来、管理者機能・プラン制限・ベータ機能などが必要になった場合に導入する。

Policy は Laravel の自動検出を優先する。

DDD のディレクトリ構成やモデル配置の都合で自動検出が分かりにくくなる場合のみ、`AppServiceProvider` などで明示的に登録する。

## Controller での認可

状態変更や詳細表示を行う Controller では、UseCase / Query を呼び出す前に認可を確認する。

認可確認は Laravel 標準の `$this->authorize()` を優先して使う。

Controller は認可確認、Request の受け取り、UseCase / Query の呼び出し、レスポンス返却に集中する。

Controller にユーザー所有判定の詳細ロジックを直接書き続けない。所有者判定は Policy に寄せる。

## Query でのユーザー境界

一覧、検索、集計などの読み取り処理では、Query 側でもログインユーザーの境界を必ず条件に含める。

Policy は個別リソースの操作可否を判断するために使い、Query は「そもそも他ユーザーのデータを取得しない」責務を持つ。

読み取り処理では、他ユーザーのデータを取得してから Vue や Controller で除外しない。

各リソースの認可実装では、Policy と Query のユーザー境界を同じ issue で完結させる。

Policy だけを追加して Query が全ユーザーのデータを返す状態、または Query だけを絞り込んで詳細表示・更新・削除の Policy が未実装の状態で完了としない。

## 作成時の所有者

ユーザー所有リソースを作成する場合、作成されるデータはログインユーザーに紐づける。

Request から `user_id` を受け取ってそのまま信頼しない。

UseCase へ渡す入力には、Controller 側で認証済みユーザーから取得したユーザーIDを含める。

## 振替の認可

振替は、振替元と振替先の両方の会計単位を扱うため、片方だけの所有者確認では不十分とする。

振替の `create` では、振替元・振替先の両方の会計単位が認証ユーザーに属していることを確認する。

振替の `view`, `update`, `delete` では、保存済みの振替に紐づく振替元・振替先の両方の会計単位が認証ユーザーに属していることを確認する。

振替一覧や検索の Query では、振替元・振替先の両方の会計単位が認証ユーザーに属している振替のみを返す。

片方でも他ユーザーの会計単位である場合、その振替操作は認可しない。

## 認可失敗時の扱い

認可に失敗した場合は、Laravel の標準的な認可失敗レスポンスを優先する。

画面操作でユーザー体験上の理由がある場合のみ、リダイレクトとエラーメッセージを検討する。

初期段階では、認可失敗が明確に確認できることを優先し、過度な独自ハンドリングは避ける。

## テスト方針

Feature テストでは、ユーザー体験として重要な代表ケースを確認する。

- 他ユーザーの会計単位を表示・更新・削除できない
- 他ユーザーの取引を表示・更新・削除できない
- 他ユーザーの会計単位を振替元または振替先に指定して振替を作成できない
- 他ユーザーの会計単位を含む振替を表示・更新・削除できない
- 認可失敗時に想定したレスポンスになる

Policy の詳細な分岐や、入力パターンの網羅は Feature テストへ詰め込みすぎない。

必要に応じて Unit または Integration テストで、Policy / Query / Validation の詳細ケースを確認する。
